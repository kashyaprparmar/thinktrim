## Important Decisions

- Created the requested repository as public `kashyaprparmar/thinktrim`; used `main` as the initial branch. The local Codex config contains machine-specific absolute paths and remains untracked. Credentials/local environment files were excluded.
- Step 35: without a shipped calibrator, `ProfileConfidencePolicy` never accepts a Jev score. Jev scores are instead surfaced as a labeled, uncalibrated advisory and cannot reorder `ranked`. If a scoped calibrator is later injected and accepts, calibrated scores may reorder only the scored top 16.
- Step 35: Jev is scoped to `thinktrim_rank` only. The sufficiency gate cannot accept an uncalibrated answer, so sending evidence there would be egress with no effect; gate and classify stay local. Egress requires `--allow-remote-data` to include every class the ranking request carries (`task`, `paths`, `summaries`). With a partial list, the server sends nothing and reports `egress_not_permitted`.
- Step 35: the API key is read only from `OPENROUTER_API_KEY`. There is deliberately no key flag, so keys cannot land in host config files or process arguments. Host key forwarding was verified against current docs: Codex `env_vars`, Claude Code `${VAR}` in `.mcp.json` `env`, and Cursor `${env:NAME}`. Setup does not write these options; hand-edited entries are treated as customized by uninstall.
- Step 35: MCP imports `JevBackend` through a narrow `@thinktrim/providers/jev` subpath, so the bundled CLI excludes the Laya sidecar client (verified in `dist/cli.js`).
- Codex's selected model and ThinkTrim's decision backend are separate. Jev is a structured decision service, not a replacement code-generating model. Enabling Jev requires the source CLI's explicit backend option, explicit remote-egress opt-in, and an OpenRouter key in the MCP process environment.
- SalesBot setup: used a project-scoped Codex MCP config and the already installed global npm package; no project dependencies or source were changed. The user-provided path spelling did not exist literally, so setup used the discovered `botrunner_qb\salesbot_back` folder.
- npm distribution/Codex migration: remove the old entry through the workspace CLI's exact-match uninstaller, then have the globally installed npm CLI write its own absolute executable path. This avoids overwriting an unrecognized or customized server entry.
- npm distribution preparation: use the available unscoped npm name `thinktrim` and publish one self-contained CLI bundle so users do not need separately published workspace packages. Node.js 20+ is required; `@iarna/toml` remains the only runtime dependency.
- Codex getting-started setup: use the project-scoped stdio MCP entry to launch the built local CLI with this repository as its workspace; no hosted backend or API key is required for deterministic retrieval/ranking.
- Step 34: addressed only measured repeated index work. Reuse extension snapshots while VS Code reports no workspace file changes and coalesce simultaneous scans; keep explicit full-content verification in the indexer. Coalesce MCP explicit refresh calls. Keep model/provider mock measurements labeled synthetic; make no real inference/startup claims from them.
- Step 33: verify file content hashes before index reuse even when timestamps match; accept the extra bounded I/O. Keep filesystem hardening within the Node CLI. Refuse symlinked ancestors and reject changed/oversized reads. Rechecking before rename narrows races but is not an OS-level atomic compare-and-swap; external credential rotation, semantic host trust, live host/model verification, and calibration remain explicit gates.

- MCP/CLI and VS Code compose one host-neutral core; the VS Code extension is optional for Claude Code, Codex, and Cursor.
- Retrieval and exact rules precede bounded inference. Ranking consumes `DecisionEngine`, not a concrete backend. Confidence/safety policy is separate from raw provider output.
- Local-only is default; remote egress and failover require explicit permission. Uncertain pruning expands or bypasses conservatively.
- Named directories are ownership boundaries, not an instruction to publish every package immediately. Step 1 added architecture only; Step 2 added package scaffolding without feature behavior.
- Initialized Git on branch `main` because the supplied workspace had no `.git` directory. TypeScript tests live outside package `src/`; package typechecks exclude tests while a root test tsconfig includes them.
- ESLint 10 is used because the initially selected ESLint 9 resolved to a deprecated unsupported release during dependency installation.
- Step 3 core depends only on `@thinktrim/shared` and Web-standard APIs. The four decision forms are binary, choice, score, and ranking; outcomes are accept, reject, retrieve_more, escalate, and unknown.
- Backend prediction and confidence policy remain separate. Exact policy can resolve a decision before backend routing. Backend selection checks supported forms, limits, data classes, locality, and health; failover only considers permitted backends. Backend outputs are validated before confidence assessment.
- Deadline and external abort are combined for the entire decision; the engine can return when a backend ignores its abort signal. Request and candidate IDs are snapshotted before asynchronous work. Structured errors and traces carry bounded diagnostic data without raw repository content.
- Root typecheck and test commands build workspace packages first so generated declarations resolve on a clean checkout.
- Step 4 verified TypeSafe Jev's OpenAPI and Laya's published Python and HTTP APIs. Shared `SystemOneRequest`/`SystemOneResponse` and `SystemOneHTTPTransport` are justified for Jev and Laya HTTP. The Python sidecar uses a separate transport and only shares question types; credentials, endpoints, lifecycle, and errors remain provider-specific.
- Native provider questions are `noul`, `choice`, and `score` against one rubric. Core ranking and per-candidate scores have no automatic native mapping. Fixture capabilities advertise only provisional binary/choice/score support; production capabilities and output conversions require implementation and validation.
- Step 5 binds the Python worker to current public `laya.Router(device=...)`, `predict`, and `predict_batch` APIs. The Router is loaded once, lazily. `THINKTRIM_LAYA_DEVICE` selects auto/cpu/cuda/mps; Laya is an optional Python dependency and weights are downloaded separately. The worker never spawns Python per inference.
- JSONL protocol V1 supports `health`, `capabilities`, `version`, `predict`, `predictBatch`, and `shutdown`, with 1 MiB frame, 32-question, and 16-item batch limits. Synchronous model inference is cancelled by terminating the worker; the Node supervisor restarts it on the next request. Raw stderr is drained but not exposed to diagnostics.
- One `LayaLocalBackend` constructs or receives one sidecar client; startup is lazy and shared across calls. Its bounded gate permits one health/preload/inference operation at a time, defaults to 32 queued requests, and rejects overflow. Shutdown drains already accepted work, rejects later work, and is idempotent. Separate backend instances intentionally own separate sidecar processes.
- The local adapter advertises binary, choice, and score only. It maps binary `noul` values to booleans while retaining the raw signal, validates choice membership, and makes a three-level per-candidate score request. `ConfidencePolicy` remains outside the adapter; ranking stays unsupported.
- OpenRouter Jev uses its Decisions API at `/api/alpha/decisions`, not chat completions. The adapter pins `typesafe/jev-1.13`; only 408/429, selected transient 5xx statuses, `ECONNRESET`, `ETIMEDOUT`, and its own attempt timeouts can be retried, within the request deadline and attempt limit. API keys and provider error bodies are never attached to errors or traces.
- Step 7 confirmed the Jev and Laya HTTP APIs share the `model`/`state`/named typed `questions` and `answers`/`usage` shape; endpoints, credentials, models, and capabilities remain provider-specific.
- `FetchSystemOneHTTPTransport` owns bounded JSON serialization/reading, content parsing, redirect rejection, cancellation, and deadlines. Each backend supplies its endpoint and headers. `LayaHTTPBackend` only accepts loopback HTTP(S) URLs before declaring `local`, defaults to `127.0.0.1:8000`, probes unauthenticated `/health`, and sends decisions to `/v1/systemone`; `JevBackend` uses OpenRouter's Decisions route, model, bearer key, and restricted retry policy.
- Step 9 keeps the repository index in memory and stores term counts plus SHA-256, not full file content. The `ignore` package applies root/nested `.gitignore` rules; hard exclusions remove common generated/dependency directories regardless of ignore negation. Symlink entries are skipped, and path resolution is checked against the canonical workspace root.
- Refresh reuses records by size and modification time, then rebuilds postings and local dependency edges. BM25 file search and line-based symbol/import extraction are deterministic and backend-independent; unresolved imports remain visible but do not produce dependency edges.
- Step 10 candidate generation is deterministic and provider-independent. It defaults to 30 candidates, caps output at 40, uses up to 20 strongest seeds for bounded graph expansion, and labels candidates with path, symbols, imports, and matched terms. Core `DecisionCandidate` objects are kept separate from local diagnostic details so they pass core request validation without extra keys. Candidate descriptions/features contain metadata and fingerprints, never source content.
- Workspace TypeScript builds now run with concurrency one in topological order so the context-ranker can consume the repo-indexer declarations on a clean build.
- Step 11 keeps deterministic ranking as the default: the labeled fixtures showed no simulated quality gain from model strategies, while scoring requires 9 grouped requests across the fixtures versus 60 binary and 15 small-choice requests. Pairwise needed 538 simulated comparisons; native listwise is unavailable in current providers. Grouped score is opt-in and capped at 16 candidates per request to fit provider capabilities.
- The ranker uses a backend result only when every score group is accepted with calibrated confidence from the same backend. Overall confidence is the minimum calibrated group confidence, never a maximum candidate score. Any failure, uncertainty, cancellation, privacy denial, or mixed backend returns the entire deterministic ordering with `confidence: null`. Score requests reconstruct labels from structured metadata and do not send caller-supplied descriptions.
- The sufficiency gate returns `insufficient` without inference when required evidence is missing or questions remain open. It returns `uncertain` for unestablished coverage, failed or unaccepted decisions, and uncalibrated or sub-threshold confidence. Only an accepted backend binary result with calibrated confidence at or above the default 0.95 floor may stop search. The floor is a conservative guard, not a measured calibration claim; local-only is the default.
- Test selection generates candidates from index facts and supplied Git diff path output. Same-package tests are a bounded deterministic fallback; inference can only reorder the selected list. The returned `alwaysRunFullCi: true` flag keeps ThinkTrim selection supplemental.
- Failure classification normalizes first, then checks deterministic signatures over the bounded normalized text. It sends only extracted exit code, error type, stack frames, test name, and relevant lines to inference; local-only is the default and uncertain model output maps to `unknown`.
- Retry gating checks attempt count, transient failure category, operation type, idempotency, prior result, cancellation, and side-effect risk before consulting any backend. Destructive, high-risk, unknown, or non-idempotent operations cannot be automatically retried; model output cannot override these denials. Eligible operations use bounded exponential delay and fall back to deterministic eligibility if inference is uncertain.
- Routing defaults to configured backend order. A named backend override is strict unless the request explicitly permits fallback; an unknown override never silently selects another backend. `local` and `remote` modes are hard filters, while `auto` allows a permitted alternate backend after failure. Remote routing still requires the request's separate data-egress permission. Optional latency and quality ranks are host-supplied hints, not calibrated backend performance claims.
- Confidence profile thresholds are expressly provisional and inspectable. Base floors vary by decision kind and profile, while category and risk floors can only raise them. No calibrator ships by default; raw provider signals cannot authorize acceptance. An injected calibrator must match backend ID, model version, category, and kind and carry evaluation provenance; the caller remains responsible for validating that evidence. Invalid mappings bypass conservatively.
